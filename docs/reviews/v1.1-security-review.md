## 1. High: an unrelated engagement lock authorizes SSH to the same execution VM

**Location:** `src/viper/cli.py:441` and `src/viper/cli.py:454`; related consumers: `src/viper/cli.py:403`, `src/viper/agents/graph.py:199`, `src/viper/execution/control.py:32`.

**Exploit scenario:** An agent for engagement A owns its project lock and uses the configured execution VM. An operator takes over engagement B, then runs `viper exec shell --project B --vm viper-kali-lab`. The shell checks only B's row, but the SSH target is independently selected by `--vm`, `--zone`, and gcloud's active cloud project. There is no trusted association between that row and the execution endpoint. A's agent remains eligible to dispatch to the same VM while the human shell opens. This can happen accidentally when an operator selects the wrong engagement. Syntactically valid names and an audit event do not bind the resources together.

**Offline reproduction:** Using temporary settings and real `ControlLock` objects, acquire A's lock as `agent`, take over B as the current human, then call `_exec_shell` for B with `subprocess.call` replaced by a recording callback. The callback runs successfully while A's holder remains `agent`. Recorded SSH arguments contain the VM and zone but no explicit cloud project. No external process was launched.

**Suggested fix:** Resolve the VM, zone, cloud project, and execution API identity from trusted configuration associated with the engagement. Have agent dispatch and human shell acquisition contend on the same canonical execution-resource lock, including when multiple engagements share a VM. Pass the configured cloud project explicitly to gcloud; the Viper engagement identifier is not necessarily a cloud project identifier. Reject shell targets that do not match the locked execution resource. Add a negative test using two engagements mapped to one VM.

## 2. Medium: the SSH lock check does not reserve control for the session lifetime

**Location:** `src/viper/cli.py:441` through `src/viper/cli.py:455`; release path: `src/viper/cli.py:469`; related code: `src/viper/execution/control.py:66`, `src/viper/execution/control.py:78`, `src/viper/agents/graph.py:199`.

**Exploit scenario:** After SSH passes the one-time holder check, another terminal can run `viper exec release --project P` while the shell is still active. An agent can acquire the freed row and dispatch concurrently with that shell. The same change can occur between the holder check and process launch. In addition, takeover only changes the SQLite row: it does not wait for an already dispatched job to stop, and the agent checks control once before its action loop. Opening SSH immediately after takeover therefore does not establish that the VM is idle. The new shell's claim that human and agent never drive the VM together is not enforced.

**Offline reproduction:** Replace the SSH subprocess with a callback representing an active session. Inside that callback, release the current human's row and acquire it as `agent`; both operations succeed before the simulated SSH session returns. Existing job continuation follows from the unchanged takeover implementation, which only performs an SQL upsert and sends no pause/stop request. No live job race was exercised.

**Suggested fix:** Establish a session-specific ownership token atomically before launching SSH and retain a reservation until the child exits. Make ordinary release refuse or coordinate with active shell sessions, and validate the current owner rather than accepting any `human:` holder. Coordinate takeover with dispatch and explicitly quiesce or wait for existing VM jobs before opening the shell. Test release during an open shell and takeover during an in-flight action.

## 3. Medium: a scope rate cap silently permits uncapped Nmap execution

**Location:** `src/viper/policy/engine.py:83` through `src/viper/policy/engine.py:90`; related code: `src/viper/tools/registry.py:38`, `src/viper/tools/real.py:30`, `vmapi/toolrunner.py:36`.

**Exploit scenario:** A scope sets `max_rate_rps: 1`. A valid Nmap action omits `rate_limit`, as its schema requires. Nmap has no registry default rate, so the policy skips the rate check and returns `REQUIRE_APPROVAL`. After normal human approval, the VM constructs an Nmap command with no rate ceiling. An operator relying on the scope cap can unintentionally authorize parallel connections and probes above the engagement's limit. Human approval is still required; this finding is that approval does not preserve the configured rate restriction.

**Offline reproduction:** Evaluate an Nmap action targeting an in-scope host with ports `22,80,443` under `max_rate_rps=1`. Result: `REQUIRE_APPROVAL`. Calling the VM's pure `build_command` function yields `['/usr/bin/nmap', '-sT', '-p', '22,80,443', 'scanme.nmap.org']`, with no rate flag. No scan was run. `tests/test_scope_limits.py::test_tools_without_a_rate_argument_are_not_rate_checked` explicitly preserves this behavior; it is an enforcement limitation, not a failing existing test.

**Suggested fix:** When a rate cap is present, deny active tools whose traffic rate cannot be bounded under that cap. Alternatively, implement an appropriate Nmap rate ceiling through the orchestrator schema, approval binding, remote request, and VM allowlist, accounting for service-detection traffic as well as port probes. If the intended cap applies exclusively to HTTP requests, represent and explain that narrower contract explicitly rather than presenting it as a general scanner cap.

## Other reviewed surfaces

- `_exec_shell` validates project, VM, and zone before constructing a list of arguments; no attacker-supplied shell expression or leading-option VM name reached the subprocess in the reviewed path (`src/viper/cli.py:438`, `src/viper/cli.py:454`). The lock findings above remain independent of argument injection.
- TSA HTTP transport retains explicit network opt-in, rejects credentials/fragments and redirects, and treats returned bytes as opaque. Offline verification checks the digest, process status, exact verification success text, and CA chain at the signed timestamp with bounded input/output and a private temporary directory (`src/viper/agents/anchor.py`). Revocation and truthful TSA time remain documented trust assumptions. No additional verification bypass was established.
- Markdown fields are escaped, evidence uses a fence longer than its contents, and JSON/SARIF use structured serialization with control/format character neutralization. Citation resolution remains bound to thread/action/tool context (`src/viper/report/generator.py`, `src/viper/report/common.py`, `src/viper/report/formats.py`). No additional injection finding was established.
- Report formats use a fixed extension map and validated thread IDs; new writes use exclusive creation (`src/viper/agents/runner.py:45`, `src/viper/agents/runner.py:56`, `src/viper/agents/runner.py:75`). CLI format selection does not introduce a traversal path.
- `_strip_ports` deliberately broadens host-and-port proposals to host scope while adding a mandatory human-review warning; drafts remain inactive until explicit approval (`src/viper/policy/scope_draft.py:352`). Paths and credentials still fail host validation. This documented approval-dependent widening was not counted as a separate bypass.
